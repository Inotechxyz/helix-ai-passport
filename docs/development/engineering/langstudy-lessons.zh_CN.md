# 开发 LangStudy 应用的经验教训

`PASSPORT ENGLISH` 是运行在 AI Passport 板上的离线优先英语学习应用：ESP32-C3、8 MB Flash、无 PSRAM、240 x 320 SPI 屏幕、三个按键。它在设备端保存单词包和学习进度，可以选择通过 HTTPS LLM API 生成新的单词包，用在线或离线方式朗读单词，并可选择把进度同步到 Azure Blob Storage。

功能参考见 [langstudy-app.md](langstudy-app.md)。本文汇总可迁移到其他受限、联网、内容生成型设备应用上的工程经验。文中的数字来自已发布的固件和真机故障抓取，而不是估算。

## 1. 让硬件约束决定架构

早期设计几乎都由约束推导而来。先写下预算，避免了大部分返工：

| 约束 | 后果 |
| --- | --- |
| 单核，无 PSRAM，SRAM 只有几百 KB | 不能有大缓冲区、解码后的图像，也不能“先分配再整理”。使用固定的 BSS 对象、流式处理和单缓冲区单一所有者。 |
| LVGL 非线程安全 | LVGL 任务之外的每次访问都要持有 `bsp_lvgl_lock()`；按键回调绝不阻塞。 |
| 8 MB Flash 但 RAM 很小 | 字体、启动画面和其他生成资源以 C 数组形式放在 Flash 中；活动单词包放在 Flash 存储里，而不是 NVS。 |
| 240 x 320，三个按键 | 单行顶栏、全屏模态状态页、短标签，以及明确的“下一步按什么”提示。 |
| 电池供电，没有墙上时钟 | 每次作答后都写入序列化状态；调度以已完成会话数为基准；SNTP 只用于 TLS。 |
| 产品承诺离线优先 | 内置单词包和离线语音合成器是必需的兜底，而不是附加功能。 |

**经验。** 在选择库之前先写内存和交互预算。在这类设备上，功能清单受限于最大的连续空闲块，而不是 Flash 容量。

## 2. 让逻辑可在主机上测试

代码分为四层：

- `components/bsp`：显示、按键、电池、音频、存储、睡眠。
- `main/langstudy_*.c` 中的纯逻辑：单词包与进度格式、调度、音素处理、IPA 转换、语音合成、JSON 提取、提示词构造、配网表单校验。
- 应用层：启动顺序、输入任务、界面和状态机。
- 服务层：配网、HTTPS 生成、Azure 同步、后台工作队列。

纯逻辑层不依赖 ESP-IDF 或 LVGL，可以在工作站上编译运行。这样昂贵的部分就变得便宜：格式往返、CRC 拒绝、调度边界情况、IPA 转换、令牌推导和清洗器行为都由主机测试覆盖。设备相关代码保持足够薄，可以通过代码审查确认。

**经验。**

- 如果代码可以是纯 C，就让它保持纯 C。主机测试只需毫秒级时间，能抓住在板子上很难复现的契约回归。
- 给每个后台任务一个消息队列，并让每个堆缓冲区只有一个所有者：任务分配并投递，UI 消费并释放。重试路径必须先释放再重新分配。
- 用同一套语料测试解析器和预校验器。本项目中，固定大小的切片扫描器和完整解析器按相同顺序执行相同规则，因此“扫描通过”就能保证“解析通过”。

## 3. 内存是核心难题

### 3.1 “空闲堆”不等于“可分配内存”

在这颗芯片上，一次 TLS 会话结束后可能仍有几十 KB 空闲，但连续可用的往往只有几 KB。实际报错为：

```text
out of memory for parsed pack (15668 bytes, free=76684)
```

在 76 KiB 空闲的情况下，15.7 KiB 的分配失败了。更早的固件在 101 KiB 空闲时也撞上了 25 KiB 的同一堵墙。TLS 之后，总空闲字节数是一个误导性的健康指标；最大连续空闲块才是预测分配成败的数字。

**经验。**

- 每次分配失败时同时记录 `esp_get_free_heap_size()` 和 `heap_caps_get_largest_free_block(MALLOC_CAP_DEFAULT)`。
- 让生命周期最长的对象静态化。活动单词包、扫描索引和缓存都是大小已知的 BSS 对象。
- 不要假设握手成功就代表堆健康。

### 3.2 TLS 之后不要分配内容大小相关的对象

第一版设计在无线电关闭后把回复解析进一个内容大小的暂存模型；第二版使用约 15.7 KiB 的 `ls_gen_pack_t`。两者都在长回复上失败，因为分配发生在堆最碎片化的时刻。

最终设计让回复缓冲区成为**唯一**与内容大小相关的分配。它在 TLS 存活时创建，SSE 响应直接流入其中（16 KiB 加上 512 字节的包装余量）。回复完成后，任务用 BSS 中固定的约 2 KiB 切片索引完成校验，并把文本缓冲区本身交给 UI。UI 重新扫描、按单词文本重映射进度、直接解析进已经常驻的 25 KiB 单词包，然后释放文本。

**经验。**

- 在传输层让堆碎片化之前分配大缓冲区，并向其中流式写入。不要在它旁边再构建第二个模型。
- 通过队列转移这一个缓冲区的所有权，并确保只释放一次。
- 缓冲区尺寸要预留协议包装（`{"pack":"..."}`）的空间。

### 3.3 双向流式处理

HTTP 任务请求 Server-Sent Events，把每个 `delta.content` 片段直接追加到单词包缓冲区。原始 JSON 响应体从不驻留内存。请求体也不物化：用相同的转义规则计算 `Content-Length`，然后从 256 字节的栈缓冲区写出字节。

流式处理也改变了超时语义：每次读取的超时只需覆盖两个 delta 之间的间隔，而不是整次生成。服务器排队的请求可能超过一分钟才发出第一个事件，因此超时设为 120 秒，同时仍不会限制一个持续有进展的生成过程。

**经验。** 对任何“相对于 RAM 而言很大”的响应，都应流式读取并增量校验。对于请求，计算长度并流式写出请求体，而不是先拼成字符串。

### 3.4 Wi-Fi 和 mbedTLS 争夺同一个堆

这是项目中最难定位的缺陷。一次 CET6 刷新在流传输到任意字节数后失败（观察到 5677 和 2242 字节），返回 `ESP_FAIL`，且 `errno` 为 0。串口日志显示：

```text
esp-aes: Failed to allocate memory
esp-tls-mbedtls: read error :-0x7180
```

mbedTLS 报告的是 `MBEDTLS_ERR_SSL_INVALID_MAC`，但根因是 AES-DMA 解密路径中的分配失败：堆被挤压得无法给驱动提供 DMA 可用的缓冲区。读取错误只是下游症状。

真正有效的修复：

- 启用 mbedTLS 动态记录缓冲区，让 RX/TX 记录内存在每个记录处理完后释放，而不是整个会话期间一直占用。
- 把 RX 记录保持在 8 KiB：更大的证书报文可能落在单个记录中，但 8 KiB 对这个端点足够。
- 把 Wi-Fi 静态 RX 池缩到 4 个缓冲（默认 10 个）。静态缓冲在 `esp_wifi_init` 时分配且永不释放，因此一直占用 TLS、AES-DMA 暂存和词包缓冲都需要的内部 RAM。为 8 个时，一次 IELTS 刷新只剩 6,272 B 空闲 / 2,048 B 最大连续块，DMA 堆为 4,068 B 空闲 / 1,152 B 最大连续块；解密路径需要 1,600 字节暂存块，另一次尝试则因最大连续块仅 14,336 B 而无法分配 16,896 B 的词包缓冲。改为 4 个后，连续四次 IELTS 刷新都以约 57–58 KB 空闲 / 30,720 B 最大连续块打开 TLS，每次都成功分配词包缓冲，流式接收期间 DMA 最大连续块仍有 8–9 KiB。
- 把 Wi-Fi 动态 RX/TX 池降到低于默认的 32（这里是 8 + 8）。SSE 回复流动时，活动集是 16.9 KiB 单词包缓冲区、动态 TLS 记录缓冲区，以及每个在途帧一个 Wi-Fi RX 缓冲区；AES-DMA 驱动还需要自己的分配。默认池大小会让解密路径饿死。
- 无线电开启期间关闭 Wi-Fi 省电；调制解调器睡眠延迟会让生成过程中的读取看起来像超时。
- 读取失败时记录 `esp_http_client_read()` 的原始返回值、`esp_http_client_get_errno()`、`esp_http_client_get_and_clear_last_tls_error()`，以及 DMA 类堆的空闲和最大块。

**经验。**

- `errno == 0` 不代表“没有错误”。对 mbedTLS 失败，要显式取出 TLS 错误码。
- 读取失败可能是更低层的分配失败。要记录 DMA 类堆，而不只是默认堆。
- 在内存紧张的 MCU 上，缓冲区调优是协议正确性的一部分。

### 3.5 分配顺序很重要

对 Edge TTS，TLS 在约 16.5 KiB 的 MP3 解码缓冲区分配**之前**建立，这样握手能拿到最大的连续块。对单词包回复，缓冲区在流式写入之前分配，传输层直接写入其中，不会让堆继续增长。正确的顺序取决于哪个操作在哪个时刻需要连续性。

**经验。** 为每次联网操作画出堆时间线：握手、头部、响应体、解码、解析、移交 UI。在碎片化程度低的点分配，在最早的安全点释放，其余对象保持固定大小。

## 4. 把生成内容当作不可信输入

LLM 回复是来自远程服务的概率性输入。保证来自校验器，而不是提示词。

请求固定了契约：单个 JSON 对象、一个 `pack` 字符串、6 行 `LESSON` 和 60 行完整 `WORD`、每词 9 个竖线分隔字段、ASCII 字段、中文翻译、ARPAbet 发音、随机且主题多样的样本，以及明确的排除列表。每次请求都带新的随机种子和随进度提升的英语等级。

设备端随后修复而不是整体拒绝：

- 把每个字段裁剪到格式上限。
- 把常见的 Unicode 标点转换为 ASCII。
- 丢弃不完整的行和模型自带的 `END` 行。
- 重写头部计数并追加新的 CRC。
- 修复发音：如果值不是 ARPAbet，先尝试 IPA 转 ARPAbet；如果仍然不可用，丢弃该 `WORD` 行。
- 丢弃单词、释义、中文翻译或发音为空的词。
- 剩余至少 30 个可用词时接受回复；只有格式错误或截断的回复才重试一次，并使用更严格的提示词和重新混合的种子。

**经验。**

- 为部分成功而设计。一个仍能支撑一次会话的短回复，比让学习者再等一次生成更好。
- 扫描器和解析器必须保持同步，并且在触碰活动单词包之前，在 UI 侧再校验一次。被拒绝的回复必须让当前单词包和进度保持原样。
- 区分“格式合法”和“可用”。`ls_pron_validate("")` 为了兼容旧单词包而故意返回 true，但空音标会产生空白发音行和无声卡片；生成路径现在会丢弃这类行。不要让兼容规则渗入新数据。
- 报告质量问题，而不是隐藏它。复用词汇不是正确性失败，因此接受并显示 `SOME WORDS REPEATED`；避免历史会阻止相同单词再次被提供。有一次抓取仍显示 60 个词全部重复，这是值得单独统计的产品质量信号，而不是静默重试。
- 重试策略应与失败类别匹配：格式错误值得再调用一次；连接、认证和内存失败不值得。

## 5. 持久化：先确定原子性单位

- 单词包和进度都是带反射 CRC32 的行式文本。解析器拒绝坏校验和、缺失的末尾换行、`CR`、`NUL`、重复 ID 和越界值。
- 单词包使用两个 Flash 槽：写入非活动槽、提交、再翻转索引。掉电后旧单词包仍然有效；损坏的槽会被跳过；两个槽都失败时加载内置单词包。
- 进度记录以稳定的单词 ID 为键，因此调整课程顺序或修改文本不会丢失历史。刷新时按裁剪后的单词文本重映射记录，并丢弃已经消失的单词。
- 每次作答后写入进度和伙伴状态，因此掉电最多丢失当前一张卡片。
- NVS 保存小型设置和 1600 字节的避免历史。大块内容放在 Flash 存储中。NVS 是键值存储，不是文档存储。
- 同步采用读取-合并-写入，并按记录比较修订号；平局时本地优先，GET 和 PUT 复用同一个 20 KiB 缓冲区。单设备假设被明确记录，而不是藏在 ETag 循环后面。
- 只有电池电量跨深度休眠保留（RTC 内存）；只有测得的电压合理时才信任它，因此睡眠中的电量计返回 `0x00` 时不会被画成 `0%`。

**经验。** 在写入第一个字节之前确定恢复方案：什么是原子的、掉电后哪一方权威、兜底是什么。然后在主机上测试损坏和截断的情况。

## 6. 小屏幕和三个按键上的 UX

- 按键回调只入队，绝不阻塞。长时间操作显示全屏状态页、`PLEASE WAIT...` 和明确的下一步。
- 在发起注定失败的请求之前检查前置条件。缺少配置时显示 `WI-FI OR DEEPSEEK NOT SET UP`（菜单中显示 `(SETUP)`），而不是等网络超时。
- 按跳报告连接状态：Wi-Fi、时钟、API。单个不透明的失败既浪费学习者的时间，也浪费开发者的时间。
- 原始诊断放在 `DOWN: DETAIL` 后面，而不是暴露在正常路径上。
- 链路图标显示最后一次验证过的状态，而不是实时 socket。每次启动后它们都从隐藏开始，由静默探测重新验证，因为重置前的结果不能说明当前网络。
- 五秒启动画面覆盖初始化，并交接给学习界面且不出现黑帧；按键唤醒跳过启动画面。
- 自动播放只在当前课程内循环，显示 `AUTO n / m`，按任意键退出且不计分，绝不跨重启保留。
- 文本简短明确，顶栏只有一行。每个新标签都要在真机上验证。

**字体经验。** 默认显示字体只有 ASCII。中文翻译需要覆盖全部 GB2312 字形的生成字体（7540 个字形，约 906 KiB 位图数据），并为控件选择正确的字体。IPA 需要自己的生成字体。在 16 px 下，部分 DejaVu 字形（小型大写 I、卷舌 schwa）看起来像缺字，因此 `ɪ` 显示为 `i`，`ER` 显示为 `ər`；UTF-8 构建成功并不能证明字形清晰可读。较长的音标水平滚动而不是换行。

## 7. 容易踩坑的联网细节

- 在 TLS 之前运行 SNTP：证书校验和 Azure 的 `x-ms-date` 头都需要合理的时钟。
- 用轻量探测检查状态。`GET /models` 能验证 key 和连接性，且不消耗生成额度。
- 每个联网功能都需要离线兜底：内置单词包、本地语音合成器、本地进度。
- 每次操作后关闭无线电可以省电，但会让每次联网操作都支付连接成本。Edge TTS 在最后一次请求后保持链路 60 秒，避免连续朗读每个单词都重新连接。
- 能力缺口很正常。IDF 5.5 当时没有内置 WebSocket 客户端，因此应用在 `esp_tls` 上实现了一个小型 RFC 6455。Edge 令牌算法绑定特定客户端版本；令牌代码和 User-Agent 必须一起升级，固定测试向量保护实现。
- 凭据字段只写不回显：留空保留已保存的密钥，复选框删除密钥，值从不写入日志或回显。Azure SAS 限定到一个容器、仅 HTTPS，并设置有限有效期。
- 接受媒体服务器可能返回过短或不完整的音频；把离线合成器作为真正的兜底，并把不合理的响应大小当作诊断信号。

## 8. 真机调试与测试

- 先复现再改代码。CET6 失败只有在完整串口日志抓取后才能解释：读取错误、AES 分配日志和 TLS 错误码一起指出了真正失败的层。
- 在组件边界埋点：请求大小、HTTP 状态、已接收字节数、原始读取返回值、TLS 错误、堆和 DMA 的空闲/最大块、解码样本数、单词包 CRC。一行有效日志胜过一天猜测。
- 为所有纯逻辑保留主机测试，为扫描器和解析器保留一致性测试。为加密或令牌算法添加固定向量。
- 为每个功能使用真机验收清单，并通过分段烧录保留 NVS 来验证持久化（本布局为 `0x0` bootloader、`0x8000` 分区表、`0x30000` 应用）。烧录后检查启动日志中的启动画面耗时、存储单词包 CRC 和缓冲区数量。
- 监视器和抓取脚本让真机工作可重复：等待 USB 端口、通过 DTR/RTS 复位、在已知标记处停止，并保留完整日志。
- 分别报告 `Build`、`Host tests`、`Device tests` 和 `Unverified`。构建成功不是硬件验证。

**工作流坑点。** Windows/WSL 共享目录可能因 CRLF shebang 失败；显式挂载 Windows 盘、把 shell 脚本行尾统一为 LF，并让构建目录归属构建用户。保留带证据表和“如何继续”步骤的 TODO/状态文档，避免上下文切换丢失调查进展。

## 9. 文档与生成资源

- 为 AI 和贡献者规则保留唯一事实来源，并链接过去，而不是复制。
- 英文和中文文档作为对齐的双语文档维护，保留互相链接；用户可见字符串变化时同时更新两者。
- 原样记录故障特征：`esp-aes: Failed to allocate memory`、`read error :-0x7180`、字节数、空闲/最大块数字。这些细节决定了后续诊断的速度。
- 用签入仓库的脚本（`tools/gen_*.py`）生成字体、启动画面和其他二进制资源，重新生成而不是手工编辑生成的 C 文件。记录源字体及其许可证。
- 绝不把凭据、二维码密钥、个人数据或未脱敏日志放进仓库或文档。

## 10. 如果重新来过

- 度量生成内容的质量，而不只是格式合法性。重复词汇率值得一个计数器和阈值；接受一个重复整个排除列表的单词包，对可用性是正确的，但对学习效果很差。
- 为每个阶段（启动、空闲、TLS 握手、流式传输、TTS、同步）写堆预算，并在诊断构建中断言。最大连续块的失败本可以在第一次真机测试前发现。
- 从第一天起就把必需字段设为必需。空发音被接受是一个向后兼容决定，后来产生了无声卡片。
- 建立可重复的多轮刷新浸泡测试并记录堆水位，而不是每次刷新时逐个发现流式失败。
- 考虑为连续 TTS 单词复用同一个 WebSocket，并增加短音频响应的合理性检查。这仍是一个未解决问题。

## 同类应用检查清单

1. 写出分阶段 RAM 预算和最大连续块目标。
2. 明确哪些对象是静态的、哪些是流式的，以及由谁释放。
3. 在接触硬件之前，让所有协议和格式逻辑可在主机上测试。
4. 把每个生成文档当作不可信输入：修复、丢弃、计数，并在交接两侧使用相同规则校验。
5. 选择持久化的原子性单位和掉电恢复路径。
6. 在边界处为每个网络跳和每次分配失败埋点。
7. 为内容、语音和同步提供离线兜底。
8. 在实际屏幕上验证字符串、字形和布局。
9. 保留验收清单，并分别报告构建、主机测试、真机测试和未验证项。
10. 记录真正重要的数字和故障特征；它们是经验中最可复用的部分。
